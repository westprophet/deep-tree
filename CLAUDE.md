# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This is the **Deep Tree** monorepo — the reference implementation(s) of Deep Tree, a file-based modular architecture for component-based UI codebases. It is the *source* of the architecture rules that get published to consuming projects (not a project that itself uses Deep Tree for a product UI).

- `packages/react` (`@redwestdev/react-deep-tree`) — the active, published React implementation. Ships `ARCHITECTURE.md` (copied into consumer projects on install) plus two small runtime utilities.
- `packages/vue` (`@redwestdev/deep-tree-vue`) — placeholder package, not yet implemented (only `package.json` + `README.md`).
- `.old/` — superseded docs (`react.md`, `vue.md`, old root `README.md`), kept for reference only. Do not treat as current.
- Full architecture documentation and rationale live in the separate `deep-tree-site-astro` repo (deep-tree.dev), not here.

**When editing `packages/react/ARCHITECTURE.md`, treat every wording change as a spec change** — this file is copied verbatim into every consuming project as the authoritative AI-assistant contract. Precision matters more than in ordinary docs.

## Commands

Package manager is **pnpm** (enforced — `npm` is blocked via the `engines` field). Requires pnpm >= 9.

```bash
pnpm install             # install deps (workspace-aware)
pnpm build               # build all packages (pnpm -r build)
pnpm test                # test all packages (pnpm -r test)
pnpm lint                # eslint . (root config covers all packages)
pnpm lint:fix            # eslint . --fix
```

Per-package (react):

```bash
pnpm --filter @redwestdev/react-deep-tree build   # tsc build, or: pnpm build:react
pnpm --filter @redwestdev/react-deep-tree publish --access public   # or: pnpm publish:react
cd packages/react && pnpm test           # vitest run
cd packages/react && pnpm test:watch     # vitest watch mode
cd packages/react && npx vitest run src/utils/createManager.test.tsx   # single test file
```

Release flow (root):

```bash
pnpm release          # build all + changeset version + publish all
pnpm release:react    # build react only + publish react only
pnpm version:all       # changeset version (bump versions from pending changesets)
```

Changesets are used for versioning (`.changeset/`, `baseBranch: main`, `commit: false`) — add a changeset (`pnpm changeset` at root, via `@changesets/cli`) for any user-facing change to a package before it can be released.

A husky `pre-commit` hook runs `pnpm lint` and `pnpm test` on every commit — don't bypass it; fix failures instead.

## Architecture

### The `react` package's public surface is intentionally tiny

`packages/react/src/index.ts` exports exactly one thing: `createManager`. The package is not a component library — it's (a) an architecture spec document and (b) two ~20-line React utilities that remove Manager/Context boilerplate:

- `createSafeContext<T>(displayName)` (`src/utils/createSafeContext.tsx`) — wraps `createContext` + a `useContext` hook that throws if used outside its provider. Internal building block.
- `createManager<T>(useController, renderOwn?, displayName?)` (`src/utils/createManager.tsx`) — built on `createSafeContext`. Returns `[Provider, useCtx]`. `renderOwn` lets the provider render its own UI (modals, toasts) alongside `children`, keyed off the controller's return value.

Any change to these utilities is a change to Deep Tree's public API for every consumer — keep the surface minimal and match the semantics documented in `ARCHITECTURE.md`'s "Manager" and "Controller" sections exactly (controller returns one object; that object becomes the provider's context value).

### `ARCHITECTURE.md` distribution mechanism

This is the core "product" of the package and its distribution is non-obvious — it's not imported, it's copied via lifecycle scripts:

1. `scripts/postinstall.js` runs automatically after `npm install` in a **consuming** project. It copies `packages/react/ARCHITECTURE.md` → the consumer's project root, and adds a `deep-tree:init` script to the consumer's `package.json`. It no-ops when running inside this repo itself (guarded by checking the script isn't under a `node_modules` path).
2. `bin/init.js` is the same copy logic exposed as a CLI (`deep-tree-react`, aliased to `deep-tree:init`) for package managers that disable postinstall scripts by default (e.g. pnpm).
3. Consumer projects are expected to feed both `ARCHITECTURE.md` and an optional local override file (`ARCHITECTURE.local.md`, *not* generated by this repo) to their AI coding assistants. On conflict, local rules win — this repo's `ARCHITECTURE.md` treats itself as a "managed file, do not edit directly by hand in the consumer."

If you change what gets copied, both `scripts/postinstall.js` and `bin/init.js` need to stay in sync (they currently share behavior but are separate files, not one shared module).

### `ARCHITECTURE.md`'s rule vocabulary

The spec uses a fixed marker vocabulary — **MUST** (mandatory), **FORBID** (prohibited), **MAY** (optional but shape-constrained if present), **SIGNAL** (not an error, flag for human review / record as an exception). When adding or editing rules, reuse these markers rather than inventing new severity language, since consumer AI assistants are instructed to key their behavior off exactly these four words.

The entity model it defines (composite vs. single entity; Page/Section/Component/Manager as specific composite-entity flavors; Layer/Group/File-Layer as folder-organization primitives; Controller as the `useController.ts` business-logic convention; Context vs. Manager as the two sharing mechanisms) is the conceptual backbone referenced throughout the docs site and any consumer's `ARCHITECTURE.md` copy — changes here ripple outward to every project that has adopted Deep Tree.
